\begin{abstract}
Repairing scientific software requires understanding the computations a change must preserve. We pre-compute expressions, conditions, definitions, and call boundaries from repository source and expose them through three query endpoints alongside the agent's ordinary tools --- a representation we call computation and boundary evidence (CBE). On 89 SWE-bench Science tasks with three runs per arm (534 verified attempts), CBE and a matched baseline solve 63 and 60 attempts respectively; the confidence interval spans zero. The discipline-level breakdown is more informative: gains concentrate where the repair corrects a calculation, losses where it must preserve an interface. Two case studies trace this asymmetry to a scope gap --- locating the relevant computation is necessary but not sufficient for a complete repair.
\end{abstract}

\section{Introduction}

Task 103 in SWE-bench Science asks an agent to repair a composite-laminate stiffness calculation in pyNastran. In the reported attempts, expanding the ply iteration without correcting the accumulation formula passes the public reproducer but fails the complete private suite. The example motivates making the computation surrounding a candidate repair directly inspectable, rather than leaving the agent to reconstruct it through text search.

CBE organizes this repository-derived evidence before repair and exposes it through three query endpoints beside the usual shell tools. Public execution observations guide source selection; static extraction links computations, conditions, definitions, and call boundaries. The baseline uses the same model, budget, and containers without this evidence store.

Our research question is whether this additional representation improves complete repair. The contributions are the preparation pipeline, query interface, and replicated comparison. We analyze both successful and unsuccessful changes to understand when the representation helps.

\paragraph{Related work.}
Bug localization through traceability links recovers connections between artifacts: RAT~\citep{niu2023rat} builds refactoring-aware trace models, ABLoTS~\citep{niu2023ablots} tests their replicability across projects, TVR~\citep{niu2025tvr} extends recovery to automotive requirements via retrieval-augmented generation, and \citet{pan2026coverage} minimise natural-language test cases under coverage constraints. These approaches link artifacts but do not extract the computational structure of the code itself. Code property graphs~\citep{yamaguchi2014cpg} unify ASTs, control flow, and data flow for vulnerability analysis; CBE borrows the multi-view graph idea but targets scientific expressions and call boundaries rather than security patterns. AutoMATES~\citep{pyarelal2020automates} and GroMEt~\citep{skema2024gromet} extract scientific models from code and equations into intermediate representations; CBE stays closer to the source, indexing expressions and conditions without attempting semantic model assembly. Tree-sitter~\citep{treesitter2024} provides the incremental parsing layer. We evaluate on SWE-bench Science~\citep{xu2026science} with DeepSeek V4.1 Flash~\citep{deepseek2026}; SWE-bench~\citep{jimenez2024swebench} and SciCode~\citep{tian2024scicode} are related benchmarks that target general software and research coding respectively.

\section{What CBE provides}
\label{sec:method}

The pipeline has three stages (Figure~\ref{fig:method}): trace, extract, query.

\paragraph{Trace.}
Run the public \texttt{reproduce.py} under an observer. The observer records which functions execute, guiding file selection for extraction. No model calls. Median duration: \MedianPreparation{}\,s of the 1800\,s budget.

\paragraph{Extract.}
Tree-sitter~\citep{treesitter2024} parses Python ASTs for scopes, assignments, binary expressions, return anchors, and branches. Joern handles C, C++, Fortran, and Cython where available; explicit fallback otherwise. External calls are labelled with their provider as interface assumptions. Unresolved callees stay \texttt{unknown\_external}.

Table~\ref{tab:representation} shows what CBE extracts for task 103 (pyNastran) --- the opening example. The computation record links the accumulation at line 1003 to its return anchor. The boundary record identifies the numpy call and its scope.

\paragraph{Query and repair.}
The agent accesses the three endpoints alongside its normal shell utilities. \texttt{find} searches the indexed structure; \texttt{inspect} retrieves computation scopes and boundary details; \texttt{note} records a working hypothesis without blocking repair. Inspection refreshes after each edit; the preparation trace stays fixed.

\section{Protocol}
\label{sec:protocol}

SWE-bench Science contains 119 tasks across 20 disciplines~\citep{xu2026science}. We use 30 tasks for development and evaluate the remaining 89, spanning 18 disciplines. Each task runs three times per arm (534 verified attempts). Both arms share the conditions in Table~\ref{tab:setup}.

A solve is a successful official verifier reward, not merely a passing public reproducer or private-test subset. All reported attempts have verdicts. We bootstrap per-task rate differences with 20,000 resamples and a fixed analysis seed; the paired sign test excludes ties.

Baseline and CBE never solve 60 and 59 tasks, respectively. Outcomes are mixed on 18 baseline and 19 CBE tasks; 11 tasks succeed in all three runs for each arm.

Figure~\ref{fig:domains} shows gains in six disciplines and losses in four. Mechanics' gain comes entirely from task 103, while the materials-science gain spans DeePTB, deepmd-kit, and dpdata. Biology's net loss comes from biopython. Each of the two largest negative differences represents one task. These groups locate where the difference concentrates.

\paragraph{Task demands and representation scope.}
The benchmark distinguishes \emph{Issue-driven}, \emph{Expert-exploratory}, and \emph{Engineering-integration} tasks~\citep{xu2026science}. These describe how a problem is posed, not its scientific discipline or the obligations of its eventual patch. A known defect still requires regression preservation; investigating an anomaly requires comparing possible explanations; integration requires checking behaviour across modules. Computation and call records are relevant to all three; whether they suffice depends on the task. Our analysis lacks per-task paradigm annotations, so we report no subgroup rates.

\section{Discussion}
\label{sec:discussion}

The two cases illustrate a pattern visible across the discipline split. When the repair obligation is correcting a calculation, CBE's evidence directly exposes the relevant scope: in task~103, the agent sees the accumulation loop, its return anchor, and the conditions guarding it, and two of three runs produce complete patches. When the obligation is preserving an existing interface, the same evidence points the agent toward internal computations rather than the function contract it must keep stable: in task~022, the agent reaches the aggregation code but alters the argument path instead of preserving backward compatibility. In these two cases, the gain came from a task whose private tests check a numerical computation and the loss from one whose tests check API behaviour. The six gaining disciplines are consistent with this pattern, though not all losses are: task~056 (aeronautical, poliastro) is a numerical repository where CBE regressed. The representation helps when what it indexes matches what the repair must preserve, and misleads when it does not.

\section{Limitations and conclusion}
\label{sec:conclusion}
CBE indexes repository evidence by task but uses the same evidence schema across repair types. Definitions and predicates are semantic cues, not specifications; the agent still forms hypotheses and checks edit implications across the workflow.

The public trace covers observed execution; extraction fallbacks and unresolved calls limit structural coverage. External providers are interface assumptions. Three replicates are insufficient for generalization claims; no ablation isolates individual components; most tasks are Python; one model and scaffold.

CBE yields similar repair rates with a resource trade-off. Whether the evidence covers the repair obligation depends on the task; extending it to cover interface and compatibility requirements is next.
